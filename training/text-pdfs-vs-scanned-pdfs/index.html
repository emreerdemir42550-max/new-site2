Text PDFs vs scanned PDFs: why one gives you words and the other gives you nothing

A PDF can contain real characters or a photograph of characters. Here is how to tell the difference in seconds, and why extraction is not OCR.

Short answer: if you can select the text in a PDF viewer, the file contains a text layer and extraction will work. If dragging across a line selects nothing, the page is an image and you need OCR — a completely different operation that this site does not pretend to do.

Two very different ways to make a PDF

A born-digital PDF is produced by software that knows what a character is. Word processors, LaTeX, browsers and report generators write text-showing operators into the page content stream: a font is selected, a position is set, and a string of character codes is drawn. The viewer maps those codes through the font’s encoding to Unicode, which is how selection, search and copy work.

A scanned PDF is produced by a scanner or a phone camera. The page contains one large image — often JPEG or CCITT-encoded — and nothing else. There are no character codes, because nobody told the file that those marks are letters. A viewer can display it perfectly and still have no idea what it says.

The difference is not about quality. A 600 dpi scan is a high-quality image of text and still has zero extractable characters. A 1998 PDF produced by a fax-adjacent tool can contain ugly bitmapped fonts and still expose every word, because the character codes are there even if the glyphs are crude.

How to tell in five seconds

  1. Open the file in a browser or reader.
  2. Try to select a sentence with the mouse.
  3. If selection highlights individual characters, there is a text layer.
  4. If the whole page highlights as a block — or nothing highlights — it is an image.

A second test: use the viewer’s find function and search for a word you can clearly see. If the search fails, there is no text layer.

PDF Text Extractor does the same test page by page and reports exactly which pages came back empty. That report is more useful than a single “extraction failed” message, because mixed documents are common: a contract can be born-digital for the first twelve pages and a scanned annex for the rest.

What extraction actually reads

For each page, PDF.js parses the content stream, tracks the text matrix as it moves, and returns items with a string, a transform and a width. Concatenating those items gives you the page’s text — approximately.

Approximation is the honest word here, for three reasons:

  • Reading order is drawing order. PDF has no notion of columns. A two-column paper is stored in whatever order the producer wrote the runs, so a naive concatenation can interleave the columns.
  • Spaces are often positional, not literal. Many producers do not emit space characters; they move the text cursor instead. Extractors infer spaces from gaps, which mostly works and occasionally does not.
  • Ligatures and unusual encodings. A font may encode “fi” as a single glyph. PDF.js maps common ligatures to their component characters, but unusual embedded subsets can produce replacement characters.

None of these are bugs in the tool; they are properties of the format.

Why OCR is a different job

OCR takes the page image and asks a model to propose characters for the shapes it sees. That means:

  • It can be wrong in ways extraction cannot. Extraction returns what the file says, even if the file says something odd. OCR returns a guess, and the guess can be confidently wrong on a serial number.
  • It needs a model. Tesseract and similar engines ship language data and are measured in tens of megabytes. That is a different weight class from a parser.
  • It is slow. Seconds per page rather than milliseconds.
  • It produces a new file. A useful OCR workflow writes an invisible text layer over the original image so the page becomes searchable while looking unchanged.

If you need OCR, use a tool that says it does OCR and shows you the recognised text for correction. A “PDF to Word” button that silently runs extraction and calls the result a conversion is the thing to avoid.

Practical consequences

  • Searchable archives: if search matters, check whether the scan pipeline writes a text layer. Many scanners can do this at capture time.
  • Compression: re-rendering pages as images — which is what Compress PDF does — removes a text layer if one existed. That trade-off is stated on the tool page for exactly this reason.
  • File size: a scanned page is usually much larger than a text page. If a 30-page document is 40 MB, it is almost certainly a scan.
  • Metadata: scanned files often carry scanner model names and timestamps in their document information dictionary. PDF Metadata Viewer & Cleaner shows them before you remove them.

FAQ

Can a PDF have both? Yes. Many OCR pipelines add a text layer to an image page. Those files select text and still look like scans.

Why does my extracted text have odd line breaks? Because each text run is positioned separately. Joining runs with spaces reproduces the visual layout only approximately.

Does extraction work on password-protected files? Only after the document is unlocked; the text layer is inside the encrypted object graph.
