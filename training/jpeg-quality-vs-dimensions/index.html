JPEG quality vs dimensions: which one actually makes a file smaller

Quality and pixel dimensions are two different levers, and one of them is much stronger. What the quality number really controls, and why resizing usually beats re-compressing.

Short answer: both levers work, but they act on different things. Quality controls how much detail the encoder is allowed to throw away; dimensions control how many pixels exist at all. Reducing dimensions removes pixels permanently and therefore almost always shrinks a file more per unit of visible damage than lowering quality does.

What the quality number controls

JPEG is a lossy transform coding scheme: the image is converted to a luminance/chrominance colour space, split into 8×8 blocks, transformed with a discrete cosine transform, and then quantised. Quantisation divides each frequency coefficient by a value from a table and rounds the result. Small coefficients become zero and disappear.

The “quality” setting in an encoder is not a standardised unit. It is a scaling factor applied to those quantisation tables. Quality 80 in one encoder is not byte-identical to quality 80 in another, and the spec does not define the mapping — which is why a file can come out larger from a different tool at the same nominal setting.

Two consequences follow:

  • Low quality hurts fine detail and edges first. High-frequency coefficients are the ones most aggressively quantised, so text, thin lines and foliage degrade before smooth skies do.
  • Re-encoding always loses a little more. Decoding a JPEG and re-encoding it re-quantises already-quantised data. This generation loss is why a “compress” tool should not be used repeatedly on the same file.

Why dimensions usually win

A JPEG’s size scales roughly with the number of 8×8 blocks it contains, which scales with pixel count. Halving both dimensions reduces the pixel count to a quarter. The encoder then has a quarter as many blocks to describe, so the file shrinks substantially even at a fairly high quality setting.

That is the practical argument for resizing first: a 4032 × 3024 phone photo displayed at 1600 px wide carries roughly six times more pixels than the display can use. Removing them costs nothing visible on the web and saves far more than dropping quality from 0.85 to 0.6 on the full-size image.

The trade-off is that resizing is irreversible. If the image might later be printed or cropped, keep the original and treat the resized copy as a derivative.

A sensible order of operations

  1. Decide the final display size. For a web hero, that is usually the CSS width at 2× for high-density screens — often 1200–1600 px, rarely 4000.
  2. Resize to that size once, with high-quality smoothing, rather than letting the browser downscale a huge image.
  3. Then pick quality. Around 0.75–0.85 is the usual range where size drops noticeably and artefacts stay hard to see at 100% zoom.
  4. Check the result at 100%, not zoomed out. Zoomed-out previews hide exactly the artefacts you are trying to judge.
  5. Compare formats. For photographic content, WebP typically produces a smaller file than JPEG at similar visual quality; for flat UI screenshots, PNG or lossless WebP is often better than JPEG at any quality.

Image Compressor exposes both levers side by side and reports the actual encoded size after each change, so the decision is made by measurement rather than by a preset name. Image Resizer handles the dimension step when that is all you need.

What the canvas encoder does, exactly

In a browser, canvas.toBlob(callback, "image/jpeg", quality) hands the bitmap to the browser’s own JPEG encoder. The third argument is a number between 0 and 1, and — as above — it is a hint, not a specification. Two browsers can produce different bytes for the same input and the same number.

Two more details matter in practice:

  • Canvas output is always 8-bit sRGB. A wide-gamut source is converted, and an embedded ICC profile is not carried into the output.
  • Alpha is discarded. JPEG has no alpha channel, so transparent areas are composited onto whatever the canvas contained — which is why a background colour control exists in conversion tools.

When compression is the wrong move

  • Text screenshots. JPEG artefacts around glyph edges are much more visible than the size saving is worth. PNG or lossless WebP wins.
  • Images that will be edited again. Every lossy pass compounds. Compress at the end of the workflow, not the beginning.
  • Files where metadata is the payload. Re-encoding through a canvas drops EXIF entirely. That is usually desirable — see what EXIF metadata reveals — but it is a change you should make deliberately.

FAQ

Does quality 100 mean lossless? No. JPEG is lossy at every setting; 100 reduces but does not eliminate quantisation.

Why did my PNG get bigger? Canvas PNG encoding is not an optimiser. For photographic PNGs, converting to WebP or JPEG usually produces a much smaller file.

Is it safe to compress the same file twice? It works, but quality degrades cumulatively. Always compress from the original.
